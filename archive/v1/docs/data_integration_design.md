# 제공 자료 검토 및 API 연결 설계

검토일: 2026-11-14. 기존 구현 설계를 보완한다. API 명세 검토와 데이터 호출 성공은 구분한다.

이 문서는 최초 자료 검토 기록이다. 이후 소량 API 호출과 관수·MCP 구현을 진행했으며, 현재 확인 결과는 [API 연결 점검](api_connection_report.md)과 [README](../README.md)를 따른다.

## 2. 문헌에서 확인한 조건과 적용 제한

### 토마토 길잡이

- PDF 43쪽 / 인쇄 40쪽: 생육 전반기 10~30 kPa, 후반기 3~10 kPa의 관리 범위를 설명한다.
- PDF 249쪽 / 인쇄 246쪽: 생육 초기~착과까지 20~30 kPa, 착과 이후 과실비대·수확기 10~20 kPa의 관리 범위를 설명한다.
- 두 절의 범위를 통합·평균하거나 임의로 하나를 우선하지 않는다. 생육단계 정의, 해당 절의 재배 맥락과 적용 범위를 먼저 검토한다.
- 관리 권장 범위가 있다는 사실만으로 관수 개시 경계의 `>` 또는 `>=`가 확정되는 것은 아니다. 연구용 이진 판정 규칙으로 바꿀 때 해석 근거와 검토 기록이 필요하다.
- kPa 수분장력, 부호를 갖는 수분퍼텐셜, pF, 부피수분함량(%)은 별도 변수로 취급한다. 센서 의미·단위·부호가 확인되기 전에는 수치 비교를 하지 않는다.
- 다른 절에 등장하는 pF/kPa 대응 표기는 원본 및 환산 관계를 추가 대조해야 한다. 텍스트 추출 결과만으로 자동 변환 규칙을 만들지 않는다.

### 전주 밭작물 물관리 지침서

- 표지에 전주 편 및 1999년 6월 7일 발행으로 표기되어 있다. 최신 적용 가능성은 별도 검토 대상으로 남긴다.
- PDF 12쪽 / 인쇄 11쪽에 `토마토(노지)` 표가 있다. 토성, 생육단계 코드, 시작·종료일, 관개간격(일), 1회 관개량(mm)으로 구성된다.
- 시설·수경 토마토에 노지 표를 그대로 적용하지 않는다. G1~G4의 단계 정의와 표의 정식 조건을 확인한 뒤 전사한다.
- PDF 2쪽의 적용 제한: 지역 일치, 파종·정식시 별도 관개, 지하수 유입 조건 제외, 평지 기준, 제시 관개요구량의 최대량 성격을 보존한다.
- 이 자료는 토양수분 센서 임계값 자료와 역할이 다르다. 노지의 일정·토성·면적을 이용한 관개량 계산 사례 후보로 분리한다.
- mm와 면적의 수량 변환은 정확한 SI 단위로 수행한다. 문헌의 평·톤 예시를 프로그램의 근사 환산 상수로 복사하지 않는다.

현재 상태는 모두 `candidate`다. 원본 PDF가 확보되었다는 이유만으로 규칙 검증을 완료 처리하지 않는다.

## 3. 비료사용처방 API

### 필지 기반 조회

로컬 명세 PDF 3~5쪽 및 벼 이외 작물 상세기능 절 기준:

- base: `http://apis.data.go.kr/1390802/SoilEnviron/FrtlzrUse`
- 벼 이외: `getSoilFrtlzrExamInfo`
- 벼: `getSoilFrtlzrExamRiceInfo`
- 인증: query의 `serviceKey`; REST GET, XML 응답.
- 핵심 입력: `PNU_Code`(19자리 문자열), `crop_Code`; 벼에는 추가 품질 코드.
- 필지에 검정자료가 있는지 먼저 확인해야 한다. 필지번호·작물코드는 숫자로 바꾸지 않고 선행 0을 보존한다.
- 사용자 지정 기본 PNU: `5211110100100120003`. `configs/data_sources.json`의 `fertilizer.default_pnu_code`에 문자열로 저장한다. 이후 시설 토마토 코드 `04017`로 시험한 결과 `301 요청 데이터 없음`이었다. 기본 PNU는 유지한다. 조회 실패 시 인증·요청 오류와 검정자료 없음을 구분해 원인을 확인하고, 필요하면 사용자가 지정한 다른 PNU로 변경한다.

### 화학성 입력 기반 체험 V2

로컬 명세 PDF 3~4·8~10쪽 기준:

- base: `https://apis.data.go.kr/1390802/SoilEnviron_FrtlzrUseExp_V2`
- 벼 이외: `getSoilFrtlzrExprnInfo`
- 벼: `getSoilFrtlzrExprnRiceInfo`
- 인증: query의 `serviceKey`; REST GET, XML 응답.
- 벼 이외 필수 입력: `crop_Code`, `acid`, `om`, `vldpha`, `posifert_K`, `posifert_Ca`, `posifert_Mg`, `selc`.
- 단위: 유기물 g/kg, 유효인산 mg/kg, 치환성 양이온 cmol+/kg, EC dS/m. 입력 유효 범위는 API 명세에 따라 별도로 검증한다.
- 출력: 밑거름·웃거름 질소/인산/칼리 및 퇴비량, kg/10a.
- 벼 코드의 `00000/00001` 표기가 명세 일부에서 상충한다. API별 코드표와 실제 응답을 대조하기 전 공통 코드로 고정하지 않는다.

API 연결 성공이 Python 시비 규칙 검증을 대신하지 않는다. 외부 처방은 공급자가 계산한 결과로 보존한다. 자체 규칙 계산과 구분하며, 같은 API 응답을 입력·정답으로 동시에 사용해 정확도를 주장하지 않는다. RAG/MCP 비교에 사용할 경우 두 경로에 제공하는 정보 범위와 정답 생성 방식을 실험 프로토콜에 명시한다.

## 4. 스마트팜코리아 API

### 시설·일자 단위 PROVIDE

명세 PDF 5·7·11·27쪽 기준:

- base: `http://www.smartfarmkorea.net/Agree_WS/webservices/ProvideRestService`
- `getIdentityDataList/{serviceKey}` → 농가·시설·지역·품목 탐색.
- `getCroppingSeasonDataList` → 작기 및 재배 메타데이터 확인. 실제 인자 순서는 해당 상세명세에 맞춰 구현한다.
- 환경: `getEnvDataList/{serviceKey}/{facilityId}/{measDate}/{fldCode}/{sectCode}/{fatrCode}/{itemCode}`.
- 시설원예 `FG`; 내부환경 `EI`, 토양환경 `EL`, 외부환경 `EO`, 양액 `NT`.
- PROVIDE 품목표: 토마토 `080300`, 방울토마토 `080600`.
- 환경 응답: `facilityId`, `measDate`, `itemCode`, `fldCode`, `sectCode`, `fatrCode`, `senVal`.

### 작기 단위 CROPSEASON

명세 PDF 5·8쪽 및 별첨 기준:

- base: `http://www.smartfarmkorea.net/Agree_WS/webservices/CropseasonRestService`
- `getCroppingSeasonDataList/{serviceKey}/{year}` → 작기 목록.
- `getCroppingSeasonEnvDataList/{serviceKey}/{croppingSerlNo}/{pageNum}` → 페이지당 1000건; 전체 페이지와 건수 기록.
- 이 문서의 품목표에는 토마토 `80300`처럼 PROVIDE와 자리 수가 다른 코드가 있다. 공통 작물명과 공급자별 원본 코드를 함께 저장한다.
- 토양환경 항목표에는 `MC` 토양함수율, `MT` 토양수분장력이 있다. 코드가 존재한다는 사실은 특정 농가에 센서 데이터가 존재한다는 보장이 아니다.

두 서비스 모두 응답의 측정값은 문자열이다. 숫자 파싱, 결측 표현, 시간대, 단위와 센서 품질 확인이 필요하다. 환경 응답에 단위 필드가 없어 단위를 임의로 붙이지 않는다. 작기 데이터의 `cntCollect`가 있으므로 원시 관측/집계 여부와 집계 방식을 확인한다.

공통 상태 코드는 첫 레코드에만 있고 이후 레코드에서는 null일 수 있다는 명세를 반영한다. 정상 응답·데이터 없음·인증 실패를 구분한다. 서비스키가 URL 경로에 들어가므로 요청 URL, 예외 문자열, 디버그 로그를 저장하기 전에 마스킹한다.

## 5. 제공 기상 서버

문서: <http://weather-rda.digitalag.kr:8001/docs>  
수신 명세: `docs/weather_openapi.json` (`info.title`: 농업 기상 데이터 API, version 1.0.0)

기상청 직접 OpenAPI와 구분해 별도 공급자 어댑터로 구현한다. 명세에는 KMA 및 RDA 자료 제공이 명시되어 있다.

우선 연결 후보:

| 기능 | endpoint |
|---|---|
| 기상청 관측소 목록 | `GET /api/kma/asos/stations` |
| 지역 목록 | `GET /api/kma/realtime/regions` |
| 최신 실황 | `GET /api/kma/realtime/latest/pivot` |
| 최신 단기예보 | `GET /api/kma/forecast/short/latest` |
| 농촌진흥청 관측소 | `GET /api/rda/weather/stations` |
| 농촌진흥청 일별 자료 | `GET /api/rda/weather/daily/range` |

공개 명세에 security scheme은 선언되어 있지 않다. 이것만으로 모든 데이터 endpoint가 무인증으로 호출된다고 확정하지 않는다. 현재 성공 확인은 `/openapi.json` 조회뿐이다.

조회 시 관측소/지역, 예보 발표시각, 예보 유효시각, 자료코드, 페이지 범위를 고정한다. 강수확률(%)과 강수량(mm)은 별도 필드이며, 기간 합산에는 명세의 시간 구간 정의가 필요하다. 관측자료와 예보자료를 섞지 않는다. HTTP 200이라도 데이터 내용의 최신성·완전성을 추가 검사한다.

## 6. 결합 방식과 구현 순서 보완

```text
외부 API → 공급자별 원본 응답 저장 → 코드·시간·단위 검증
        → 정규화 스냅샷 → 동일한 RAG / MCP 입력
원본 PDF → 쪽/절별 기준 후보 → 적용 조건 검토 → 승인된 규칙
```

최초 범위는 토마토를 후보로 두되, 토경·수경·노지를 구분한다. 실제 스마트팜 농가의 재배방식과 수분장력 단위가 맞아야 토경 기준과 연결할 수 있다. 지역 기상은 실내 센서값을 대신하지 않는다. 스마트팜 시설과 흙토람 필지를 지역명만으로 동일 농장이라고 결합하지 않는다. 필지/시설 매핑이 없으면 서로 다른 자료 또는 분리 사례로 표시한다.

다음 구현 순서:

1. 공급자 어댑터·공통 스키마와 비밀정보 마스킹 구현.
2. 기상 소량 조회 및 스마트팜 시설·작기 탐색; 실제 값·기간·센서·단위 확인.
3. 토마토 기준 후보에서 하나의 적용 맥락을 선정하고 독립 검토.
4. 확정된 스냅샷으로 관수 엔진과 실제 MCP 연결.
5. 비료 체험 API는 필수 토양 화학성이 확보된 사례부터 별도 연동.

이후 외부 소량 데이터 호출을 진행했다. 농업 규칙 확정·연구 실험은 아직 수행하지 않았다.

## 7. 검토 도구와 보관

- `scripts/inspect_sources.py`: 로컬 PDF 텍스트를 PDF 쪽 번호와 함께 추출. 인증키 파일은 읽지 않는다.
- 실행: `python scripts/inspect_sources.py` (현재 `.tools/pdf`에 설치된 pypdf 사용).
- 추출 텍스트와 원본 검토 이미지는 `outputs/source_review/`에 보관한다. 스캔 표는 텍스트 추출로 검증되지 않으므로 원본 이미지를 사용한다.
- `.gitignore`에 현재 인증키 파일, 환경 변수 파일, 로컬 도구와 산출물을 제외했다. 기존 추적 여부를 변경하거나 인증키 원본을 이동하지 않았다.
